# Retrospective

이 문서는 FOMO Guard 프로젝트의 회고입니다. 기능 구현 결과보다 프로젝트를 통해 어떤 문제를 이해했고, 어떤 선택을 했으며, 다음에는 무엇을 개선할 수 있는지 정리합니다.

## 프로젝트를 통해 배운 점

### 1. 좋은 대시보드는 숫자를 많이 보여주는 화면이 아니다

처음에는 자산 비중, 수익률, 평가금액을 많이 보여주면 좋은 대시보드가 될 것이라 생각할 수 있습니다. 하지만 FOMO Guard를 만들면서 중요한 것은 숫자의 양이 아니라 해석의 방향이라는 점을 배웠습니다.

사용자는 단순히 "얼마나 올랐는가"보다 "내 판단이 어떤 흐름에 영향을 받았는가"를 알고 싶을 수 있습니다. 이 프로젝트는 그 질문을 화면 구조와 인사이트 문장으로 풀어보는 시도였습니다.

### 2. 금융 서비스는 기능보다 문구가 더 위험할 수 있다

분석 결과를 보여주는 문장 하나가 투자 추천처럼 보일 수 있습니다. 그래서 기능 구현만큼이나 표현 가드레일이 중요했습니다.

프로젝트에서는 다음 원칙을 지켰습니다.

- 특정 종목을 사라고 말하지 않는다.
- 특정 자산의 미래 수익을 예측하지 않는다.
- 위험을 단정하지 않고 점검할 수 있는 방향을 제시한다.
- 사용자의 판단을 비난하지 않는다.

### 3. 제출용 MVP에서는 안정성이 설득력이다

실시간 API 연동은 매력적이지만, 제출 환경에서는 실패 가능성을 키울 수 있습니다. 이 프로젝트에서는 정적 웹앱, 샘플 CSV, 클라이언트 분석을 선택했습니다.

이 선택은 화려함보다 재현 가능성을 우선한 결정이었습니다. 데모를 보는 사람이 바로 실행할 수 있어야 한다는 점이 해커톤 제출물에서는 중요한 기준이었습니다.

## 한 문장 회고

FOMO Guard는 "무엇을 살지"를 알려주는 프로젝트가 아니라, "왜 지금 사고 싶어졌는지"를 스스로 묻게 만드는 프로젝트였습니다.
