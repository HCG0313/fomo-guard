# Troubleshooting

이 문서는 FOMO Guard 개발과 제출 과정에서 겪은 문제, 원인, 해결 방법을 정리한 기록입니다. 단순 결과물이 아니라 문제를 어떻게 정의하고 해결했는지 보여주기 위한 포트폴리오 근거입니다.

## 문제 해결 요약

| 문제 | 원인 | 해결 | 배운 점 |
| --- | --- | --- | --- |
| 단순 수익률만으로 FOMO 설명이 어려움 | 수익률은 결과일 뿐 포트폴리오 형성 과정을 설명하지 못함 | 매수일, 최근 수익률, 비중 변화율을 함께 보는 시간 흐름 기반 진단으로 전환 | 투자 데이터도 맥락을 함께 봐야 의미가 생김 |
| CSV 데이터가 부족할 수 있음 | 사용자가 모든 시간 정보 컬럼을 넣지 않을 가능성 | `timeline_based`, `snapshot_estimated`, `insufficient_data` 상태로 진단 수준 분리 | 부족한 데이터에서도 가능한 분석 범위를 명확히 해야 함 |
| 인사이트가 투자 추천처럼 보일 위험 | 금융 대시보드 문구가 쉽게 매수/매도 권유처럼 읽힐 수 있음 | 점검형 표현만 사용하고 금지 표현을 규칙 문서에 명시 | UX 문구도 서비스 정책의 일부 |
| 외부 API 사용 시 데모 불안정 가능성 | API 키, 네트워크, 인증 문제로 심사 환경에서 실패 가능 | 정적 웹앱과 샘플 CSV 중심으로 구성 | 제출용 MVP는 재현성과 안정성이 중요 |
| FOMO 점수 산식이 규칙 문서와 어긋날 수 있음 | 구현 중 점수 항목이 문서 기준과 다르게 반영될 위험 | 최종 검증에서 점수 항목을 규칙서 기준으로 재정렬 | 문서와 코드가 같은 기준을 공유해야 함 |
| 콘솔에 favicon 404 발생 | 브라우저가 기본 favicon을 요청했으나 파일이 없음 | data URL favicon 추가 | 작은 콘솔 오류도 제출 전 정리 대상 |
| GitHub 업로드 구조가 헷갈림 | 웹사이트 파일과 PDF 문서 위치가 섞일 수 있음 | 루트에는 README/PDF, `fomo-guard-site/`에는 웹앱 소스를 두는 구조로 정리 | 저장소 구조도 평가자가 보는 UX |

## 대표 문제 1. FOMO를 수익률로만 설명할 수 없었다

초기에는 자산별 수익률과 비중을 계산하면 FOMO 위험을 어느 정도 설명할 수 있을 것이라 생각했습니다. 하지만 같은 비중이라도 오래 보유한 자산과 최근 급등 후 편입한 자산은 전혀 다른 의미를 가집니다.

해결 방법:

- `purchase_date`를 기준으로 최근 편입 여부 계산
- `recent_7d_return`, `recent_30d_return`으로 최근 급등 여부 판단
- `weight_change_7d`, `weight_change_30d`로 비중 확대 여부 확인
- 단일 조건이 아니라 복합 조건으로 FOMO 위험 판단

## 대표 문제 2. 추천 서비스로 오해될 수 있었다

FOMO 위험을 "높음"으로 표시하면 사용자가 특정 자산을 팔아야 한다는 의미로 받아들일 수 있습니다. 이 프로젝트의 목적은 투자 판단을 대신하는 것이 아니라, 사용자가 스스로 판단 근거를 점검하도록 돕는 것입니다.

해결 방법:

- 금지 문장 정의: "매수해야 합니다", "매도해야 합니다", "유망합니다" 등
- 허용 문장 정의: "가능성이 있습니다", "점검이 필요합니다", "확인해보는 것이 좋습니다"
- 인사이트를 최대 3개로 제한해 핵심 위험만 전달

## 대표 문제 3. 제출 환경에서 실패하지 않아야 했다

외부 금융 API를 사용하면 더 실제 서비스처럼 보일 수 있지만, 해커톤 심사 환경에서는 API 키와 네트워크 이슈가 실패 요인이 될 수 있습니다.

해결 방법:

- 정적 HTML/CSS/JavaScript로 구현
- Netlify에 정적 배포
- 기본 샘플 데이터 포함
- CSV 업로드 방식 제공

결과적으로 심사자는 별도 계정, API 키, 설치 없이 URL만으로 서비스를 확인할 수 있습니다.
